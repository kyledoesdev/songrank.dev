## Project Overview

songrank.dev — a Laravel 13 application with two ways to order music, and one way to write about it:

- **Rankings** turn a Spotify artist, playlist or podcast into a fully ordered list through pairwise comparisons driven by a merge-sort algorithm.
- **Tier lists** place artists, albums or tracks into named tiers on a drag-and-drop board.
- **Reviews** score one artist, album or track out of ten in half stars, with a written body.

Users authenticate with Spotify. A finished record of any kind can be made public, browsed from the explore page and commented on; rankings can also be exported.

The **Catalog** sits on top of all three: each user files their own rankings, tier lists and reviews into folders called **crates**, and one record can sit in as many crates as they like. A catalog is private unless its owner makes it public, which lets anyone browse it from their profile.

## Architecture

### Routes

`routes/web.php` holds the public and account routes, then requires one file per domain: `routes/rankings.php`, `routes/billing.php`, `routes/tierlists.php`, `routes/reviews.php` and `routes/catalog.php`. Pages are Livewire components registered with `Route::livewire()` and titled with `->withHead()`.

Developer-only routes use `IsDeveloper` from `kyledoesdev/essentials`.

The show routes (`/rank/{id}`, `/tierlist/{id}`, `/review/{id}`) are public because a finished, public list is meant to be shared; the component decides who may actually see each record (`canBeSeen()`), and serves the sorting process itself to an owner whose list is not finished yet. Crate pages (`/catalog/{id}`) are the exception: they sit behind auth, and `Crate::canBeSeen()` keeps each one to its owner.

### Action Pattern

Business logic lives in `app/Actions/` rather than in controllers or Livewire components, organized by domain:

- `Actions/Rankings/` — ranking creation, update and deletion (`StoreArtistRanking`, `StorePlaylistRanking`, `StoreShowRanking`, `UpdateRanking`, `DestroyRanking`). `CompleteSongRankProcess` sits at the `app/Actions/` root rather than in here.
- `Actions/Reviews/` — review lifecycle (`StoreReview`, `UpdateReview`, `PublishReview`, `DestroyReview`), `ResolveReviewSubject` for turning a search result into a local model, and `CleanReviewBody` (see **Reviews** below)
- `Actions/Tierlists/` — list lifecycle (`StoreTierlist`, `UpdateTierlist`, `DestroyTierlist`, `CreateDefaultTiers`, `MoveTierlistItem`, `CompleteTierlist`, `ResolveTierlistEntries`), with tier CRUD under `Actions/Tierlists/Tiers/`
- `Actions/Catalog/` — crates and what is filed in them (`StoreCrate`, `UpdateCrate`, `DestroyCrate`, `MoveCrate`, `ReorderCrate`, `UpdateCatalogSort`, `AddCrateItem`, `RemoveCrateItem`, `MoveCrateItem`, `SyncEntityCrates`). They trust their caller: ownership and Pro checks live in the Livewire components (see **Catalog** below)
- `Actions/Spotify/` — every Spotify API call (`SearchArtists`, `SearchAlbums`, `SearchTracks`, `GetArtistSongs`, `GetArtistAlbums`, `GetPlaylistTracks`, `GetShowEpisodes`, `RefreshToken`). `GetArtistAppearsOnSongs` is deliberately separate: featured tracks are expensive to fetch for prolific guests, so `count()` probes cheaply during artist selection and `handle()` only runs when the user toggles the featured list on
- `Actions/Artists/`, `Actions/Playlists/` — resolve a Spotify payload into local models
- `Actions/Billing/` — the Song Rank Pro purchase lifecycle (`StartProCheckout`, `FulfillProPurchase`, `RevokeProLicense`, `GrantProLicense`, `HandleStripeWebhook`)
- `Actions/Comments/` — comment mention resolution and profanity filtering
- `MaskProfanity` sits at the `app/Actions/` root and covers names. Every ranking, tier list, review, tier and crate name is masked by its store and update actions, public or not. Rankings, tier lists and reviews pass the name of their source or subject as `keep`, so the Spotify name a default name borrows is never touched

### Livewire Components

The primary UI layer. Each page is a Livewire component in `app/Livewire/`:

- `SongRank/SongRankSetup` — a shell that renders the setup component for the chosen `RankingType` (mapped in `setupComponent()`). Each of `SongRank/Setup/{Artist,Playlist,Show}Setup` owns its own search, track selection and persistence
- `SongRank/SongRankProcess` — the core pair-comparison UI, with `SongRank/ProgressTabs/` and `SongRankProgressModal` beside it
- `Tierlist/TierlistSetup` — the same shell pattern for `TierlistType`, dispatching to `Tierlist/Setup/{Artist,Album,Track}Setup`
- `Tierlist/TierlistBuilder` — the drag-and-drop board; `Tierlist/TierlistPanel` is its read-only counterpart
- `Reviews/ReviewSetup` — the same shell pattern for `ReviewType`, dispatching to `Reviews/Setup/{Artist,Album,Track}Setup`. Setup only picks the subject and the settings; the review is written in `Reviews/EditReview`, which is both the draft editor and the edit page
- `Reviews/ReviewShow`, `Reviews/ReviewPanel` (dashboard) and `Reviews/Card`
- `Dashboard/Dashboard` and `Dashboard/InProgress` — the user's rankings and lists
- `Explorer`, with `Explorer/RankingsFeed`, `Explorer/TierlistsFeed` and `Explorer/ReviewsFeed` — browse public records. The three feeds share `Livewire/Concerns/HasInfiniteFeed`
- `Ranking/Ranking`, `Ranking/EditRanking`, `Tierlist/TierlistShow`, `Tierlist/EditTierlist` — view and manage one record
- `Catalog/Catalog` and `Catalog/CrateShow` — the catalog and one crate's page, sharing `Catalog/Concerns/HasCrateList`. `Catalog/CrateSettings` is a crate's cog popover, `Catalog/AddToCrateModal` files records from inside a crate, and `Catalog/CratePicker` files one record into crates from its setup form or its finished show page. `Catalog/CatalogModal` is the read-only catalog a profile opens
- `Profile/Profile`, `Profile/Settings`, `Billing/Billing`, `Navigation`, `Notifications/ShowAll`

Shared behaviour lives in traits rather than base classes: `Livewire/Concerns/InteractsWithAlerts` centralizes flash messaging for every component (see **Alerts** below), and per-domain concerns sit in `SongRank/Concerns/` (`HasTrackList`, `HasRankingForm`, `HasSetupFlashErrors`) `Tierlist/Concerns/` (`HasEntryBank`, `HasTierlistForm`, `HasTierlistFlashErrors`) `Reviews/Concerns/` (`HasReviewSubject`, `HasReviewForm`, `HasReviewFlashErrors`) and `Catalog/Concerns/` (`HasCrateList`, `FilesIntoCrates`). Form objects are in `Livewire/Forms/`, and shared markup in `resources/views/livewire/{song-rank,tierlist}/setup/partials/`.

### Alerts

Two separate things, deliberately not merged:

- **`Livewire/Concerns/InteractsWithAlerts` is sweetalert2.** `flash()` and `confirmAction()` encode a payload and hand it to `resources/js/alerts.js` through `$this->js()`. A confirm calls back into the asking component by Livewire id. Its confirm button is primary purple, except a delete, which passes `destructive: true` (to `confirmAction()` or to an inline `window.confirm({...})`) for the red `btn-danger` one; `alerts.js` owns the button classes, so a caller never styles them. This is the dialog system; leave it alone.
- **Session flashes are Flux toasts.** `App\Livewire\SessionToasts` is mounted once in the layout and raises a toast from `mount()` for `session('success')` and the error bag. `Flux::toast()` needs a live Livewire component to dispatch from, which a full page load otherwise has nowhere to find.

Flux is installed for toasts and the review editor only. Nav, cards, buttons, inputs, dialogs and theming stay homegrown. Flux's dark theme is gated behind a `.dark` class the layout pins off, because this app is light only.

### Key Models and Relationships

- `User` → has many `Ranking`, `Tierlist`, `Crate` and `ProLicense`; has one `UserPreference`. Allowance logic lives in `Models/Concerns/HasRankingAllowance`, `HasTierlistAllowance` and `HasCrateAllowance`
- `Ranking` → belongs to `User`, has many `Song`, has one `RankingSortingState`, and has a polymorphic **`source()`** — an `Artist`, `Playlist` or `Show`. There are no per-type foreign keys any more; anything needing the source reads `source`, and `RankingType` says which kind it is
- `Tierlist` → belongs to `User`, has many `Tier` (the first of which is the bank) and many `TierlistItem`. Its `source()` is polymorphic too, but records **provenance only** — a list assembled from search has none
- `TierlistItem` → belongs to a `Tier` and morphs to an `entryable`: an `Artist`, `Album` or `Track`
- `Review` → belongs to `User` and morphs to a `subject`: an `Artist`, `Album` or `Track`. Soft deletes, so one-review-per-subject is enforced in `HasReviewSubject` rather than by a unique index
- `Song` → `featured_artist` marks tracks the ranked artist only guests on; for those rows `artist_id` points at the track's *primary* artist, while every other row's `artist_id` is the artist the *ranking* belongs to
- `RankingSortingState` — persists merge-sort algorithm state so rankings can be resumed across sessions
- `Crate` → belongs to `User`, nests through `parent()` / `children()`, has many `CrateItem` and may have a `CrateIcon`. `CrateItem` morphs to an `entity`: a `Ranking`, `Tierlist` or `Review`
- `Ranking`, `Tierlist` and `Review` implement `Contracts/CrateEntity` (`cover()`, `label()`, `progressLabel()`, `url()`, `canBeEdited()`, `crateItems()`) and use `Models/Concerns/BelongsToCrates`, which is what lets any of them be filed in a crate and listed the same way
- `Artist`, `Album`, `Track`, `Playlist` and `Show` all implement `Contracts/SpotifyEntity` (`name()`, `cover()`, `spotifyId()`, `spotifyUrl()`) — that shared shape is what lets a ranking source, a tier list source, a tier list entry and a review subject each be any of them

### Custom Query Builders

Every model with non-trivial reads has a builder in `app/QueryBuilders/`, attached with `#[UseEloquentBuilder]`. Page-shaped scopes are named after the surface they serve — `forExplorePage()`, `forProfilePage()`, `forDashboard()`, `forNewsletter()` — so a page's query lives in one place instead of being assembled inside the component. Prefer adding a scope there over writing a query inline.

### Enums

`App\Enums\RankingType`, `App\Enums\TierlistType` and `App\Enums\ReviewType` carry their own presentation (`label()`, `icon()`, `color()`, `filamentColor()`), so neither Blade nor Filament needs to match on a raw string. `CrateEntityType` does the same for the three kinds of record a crate holds, and maps each to its model (`model()`, `query()`). Billing enums live under `Enums/Billing/`.

### Global Helpers

`app/global/functions.php` is autoloaded via the `files` array in `composer.json`.

### SEO

All page-level SEO logic (OG tags, Twitter cards, canonical URLs, JSON-LD structured data) lives in `app/Seo/`, one class per page surface. Each class owns the full set of `Head::` calls for that page; the Livewire component or controller just news it up and calls `handle()`.

- `RankingPage` — OG/Twitter/canonical + `ItemList` schema for public finished rankings
- `TierlistPage` — OG/Twitter/canonical + `ItemList` schema for public completed tier lists
- `ReviewPage` — OG/Twitter/canonical + `Review` schema with `Rating` for public reviews
- `FaqPage` — `FAQPage` schema from active FAQ entries
- `WelcomePage` — `WebApplication` schema with pricing tiers and author

The site-wide default meta description and OG/Twitter fallbacks are configured in `AppServiceProvider::configureHead()`. SEO keywords come from `ApplicationDashboard::seoTerms()`, cached for a week and busted by `ApplicationDashboardObserver` on save.

## Feature Flags

Three Pennant flags exist (`songrank-pro`, `tierlists`, `reviews`) but all three are fully released — each resolves true for any signed-in user and false for a guest. Nothing in the app checks them; what a free account can do is limited by Pro, not by a flag. `pennant:purge` is a routine deploy step. A flag is a rollout switch and nothing more — it never answers "has this person paid?" (see Song Rank Pro below).

## Tier Lists

- Three types (`TierlistType`: artist, album, track). In the UI they are named "by Artist / by Album / by Track" — "album tier list" on its own reads as *ranking the tracks on one album*, which is not what it is.
- The board's shape is `config/tierlists.php`: `max_tiers`, the `default_tiers` every new list starts from, and the **bank**. The bank is a tier row like any other so that every item carries a tier id and every drag target is uniform — but it always sits at position zero, cannot be renamed, reordered or deleted, and must be emptied before a list can be finished (`Tierlist::bankIsEmpty()`).
- Per-type list limits live in `config/billing.php` under `tierlist_limits`, and the per-list entry ceiling under `tierlist_item_limits`. That second one is **never null**: a board has to stay draggable, and every tile is an image the browser has to paint.
- `TierlistBuilder` keeps Spotify embeds off by default — every player is a cross-origin document to build.
- Publishing locks a free account's board: `Tierlist::canBeRearranged()` (owner, and unfinished or on Pro) is checked when the builder mounts and again on every request through its `hydrate()`, because a builder left open in another tab outlives the publish. The show and edit pages draw a read-only board for the same rule.

## Reviews

- Three types (`ReviewType`: artist, album, track). One `stars` column holds the score in half steps from 0 to 10; the "8.5/10" form is the same value formatted by `Review::score()`, not a second column.
- A review starts as a **draft** and publishing is one way (`PublishReview` never moves `published_at`). Settings stay editable by the owner; the content (stars and body) is editable after publishing only on a Pro account — `EditReview::canEditContent()` decides, and the server ignores submitted content when it says no.
- Free accounts get five reviews in total across every type (`config/billing.php` → `review_limits`); drafts count, and deleting frees a slot.
- **The body is user-authored HTML rendered unescaped.** `CleanReviewBody` is the only way in: `symfony/html-sanitizer` with an explicit allowlist first, then Blasp on the text *between* tags only (Blasp mangles tag characters). It also derives `body_text`, the plain copy used for search and excerpts. Anything that writes `body` must go through it — the Filament form deliberately has no body or stars field.
- Sharing is X, Bluesky and copy-link (`ShareTarget`), plus review-specific OG/Twitter tags from `laravel/head` — only when the review is public.
- `DeleteUserJob` deletes a user's reviews and tier lists along with their rankings; a soft-deleted author left behind breaks pages that read `->user`.

## Catalog

- A catalog is the user's **crates**: folders for their own rankings, tier lists and reviews. A record goes in any number of crates, once each, and nothing is filed automatically — the user picks every crate.
- A catalog is private until its owner opens it up in Settings (`user_preferences.catalog_is_public`, read through `User::hasPublicCatalog()`). Only then does the profile card grow a footer that opens `CatalogModal`, for guests too. Inside, a visitor sees only records that are public and finished (`CrateItemQueryBuilder::whereEntityIsPublic()`), and crate counts count only those; the owner sees everything. The modal checks visibility on mount and again on every step into a crate, so going private takes effect at once. Crate pages themselves stay the owner's management screens.
- Limits live in `config/billing.php` → `catalog_limits`. `folders` counts every crate the user owns, nested or not (`null` is unlimited); `depth` is how many levels a catalog may go, so free is 5 flat crates and Pro is unlimited, nested one level. Losing Pro keeps everything already made but stops new crates and nesting.
- Nesting is `parent_id` plus a stored `depth`, never a fixed shape. `MoveCrate` and `Crate::branch()` walk the tree generically, so going deeper is a config change.
- Positions run from zero with no gaps inside each list (a crate's siblings, a crate's items). A new row takes the end through a `creating` hook on its model, and anything that removes or moves a row keeps the run tight through `QueryBuilders/Concerns/HasPositions`. Items drag into order on any account; crates only on Pro, and only while `user_preferences.catalog_sort` is `custom` (`CatalogSort`). Free accounts always read A–Z.
- `crate_items.entity_type` stores the **full class name**. `Ranking`, `Tierlist` and `Review` are deliberately kept out of the morph map: aliasing them would change what Spatie Comments writes to `commentable_type` and orphan every existing comment.
- `BelongsToCrates` takes a deleted record out of every crate it was in. Soft deletes never reach the database cascade, and the admin panel deletes rankings without going through `DestroyRanking`, so the clean-up hangs off the model. `DeleteUserJob` deletes the user's crates first.
- **Authorization lives in the Livewire components.** `CrateSettings`, `AddToCrateModal` and `CratePicker` only ever render for the owner and check once in `mount`. `CrateShow` serves anything `Crate::canBeSeen()` allows (only the owner, today) and still guards its edits (`moveItem`, `removeItem`) with `canBeEdited()` on their own.
- `CratePicker` sits in every setup form and on the owner's view of a **finished** ranking, tier list or review — deliberately not unfinished ones, to nudge people to finish. In a setup it binds `crateIds` with `#[Modelable]`, and the setup files the new record through `FilesIntoCrates` after its Store action; on a show page each tick files straight away.
- Crate icons are rows in `crate_icons`, managed from the **Crate Icons** admin page (`is_pro`, `is_active`, drag order) and seeded by `CrateIconSeeder` from their create-table migration. Font Awesome loads from a kit, so seeded icons stay in the free solid set; `AdminPanelProvider` loads the same kit through a `HEAD_END` render hook so the previews draw. A crate's colour is any hex the native colour picker gives, validated by `Livewire/Forms/CrateForm`.

## Song Rank Pro (Billing)

A one-time $10 purchase.

The Pennant flag (`songrank-pro`) is a rollout switch, not an entitlement — **never grant Pro by activating a Pennant flag.** A `pro_licenses` row answers "has this person paid?"

`users.is_pro` is a projection of the licences table, not a second source of truth. `ProLicenseObserver` recomputes it whenever a licence is saved, deleted or restored, so `$user->is_pro` is a column read rather than a query — it is called from the nav, the setup header, the middleware and the billing page on a single page load. The one gap is mass assignment: `ProLicense::query()->update(...)` fires no model events, so anything doing that must call `$user->syncProStatus()` itself (`DeleteUserJob` is the only place that currently does).

Other notes:

- Cashier's `WebhookController` handles only eight subscription-shaped events. The one-off purchase lifecycle is ours, routed by `HandleStripeWebhook` off the `WebhookReceived` event. Stripe's event names and payment statuses are modelled as `StripeWebhookEvent` and `StripePaymentStatus` — resolve them with `tryFrom()` rather than comparing raw strings, and note that Stripe event names contain dots, so they can never be looked up with `data_get()`.
- Fulfillment runs from both the webhook and the success redirect, and Stripe retries webhooks for three days, so it must stay safe to run repeatedly. It **claims** the license with a single conditional `where status = pending` update and checks the affected row count — reading the status into PHP and then writing would leave a window where two callers both pass the check and both send a receipt. The loser backfills any field the winner could not populate (Stripe raises the invoice asynchronously, so an early caller can see `session.invoice` as null).
- `config/cashier.php` pins `webhook.events` to `StripeWebhookEvent`, **not** Cashier's `DEFAULT_EVENTS`. The defaults are all subscription-shaped; leaving them would make `php artisan cashier:webhook` create an endpoint that never delivers `checkout.session.completed` and silently stops every purchase from fulfilling.
- Never let a money event pass in silence. A refund or chargeback for a payment intent no license claims is logged loudly to the `discord_billing_updates` channel, because Stripe will keep retrying the original `checkout.session.completed` and could hand Pro to somebody already refunded.
- Money is stored in integer minor units and displayed via `Cashier::formatAmount()`. Never floats.
- **Store as little as possible.** No card brand or last four, no payment-method columns on `users`, no trial columns, and no subscription tables — Cashier's published migrations for those were deliberately removed. Stripe holds the card; we hold an invoice URL. Anything added here has to be disclosed in the privacy policy, so the bar is "the product genuinely cannot work without it".
- Limits live in `config/billing.php` (`null` means unlimited, never a sentinel like `PHP_INT_MAX`). On the model they read as `rankingLimit()` / `canCreateRanking()` and `tierlistLimit()` / `canCreateTierlist()`. The block is a UI one: `setup-header.blade.php` swaps the search box for an upgrade prompt when the limit is reached, so a capped user never gets as far as a search. The `ensureCanCreateRanking()` / `ensureCanCreateTierlist()` calls at the top of each setup component's `search()` are only a backstop for stale pages. **There is no ranking or tier list policy** — being told 403 after clicking "begin ranking" is the wrong place to find out.
- The checkout session is treated as a resource: `store`, `show` and `cancel`. `show` and `cancel` answer GET because Stripe redirects the customer's browser to them. Entitlement is handled by `RedirectIfAlreadyPro` on the route, which is also throttled, and `store` sends the buyer back to billing with an error when Stripe cannot be reached.
- A buyer has one open checkout at a time: `StartProCheckout` expires any session they left open in another tab before opening a new one. Stripe refuses to expire a session that has already been paid, and that licence stays pending for fulfillment. If a second payment still lands for somebody already on Pro, fulfillment flags it to `discord_billing_updates` for a refund and sends no second welcome.
- Invoice PDFs come from Stripe (`invoice_creation` on the checkout session). There is no PDF library and none should be added.
- Automatic tax is opt-in via `STRIPE_AUTOMATIC_TAX`, and gates both `Cashier::calculateTaxes()` and the session's `automatic_tax`/`tax_id_collection`. Sending those before the Stripe account has a head office address makes Stripe **reject the whole checkout session**, so it stays off until Stripe Tax is genuinely configured.
- `ProPurchaseReceipt` welcomes the buyer to Pro over the `mail` and `database` channels (`emails.pro-purchase-receipt`). Stripe sends its own payment receipt, so this one points at what they just unlocked rather than restating the charge.

## Admin Panel

Filament 5 at `/admin`, restricted to users with the `is_dev` flag via the `IsDeveloper` middleware. `CommentResource` skips authorization: Spatie's comment policy lets only a comment's author edit or delete it, which would leave the panel unable to moderate. The comment relation managers defer to the resource, and like every relation manager they are read-only on view pages, so moderation happens from the edit pages. Resources live in `app/Filament/Resources/<Plural>/`, each with the `Pages/`, `Schemas/`, `Tables/`, `Filters/` and `RelationManagers/` subdirectories it needs. Shared pieces are in `app/Filament/Concerns/` (`HasCachedNavigationBadge`, `HasDateFilters`); dashboard widgets are in `app/Filament/Widgets/`.

Namespaces that are easy to get wrong: form fields are `Filament\Forms\Components\`, infolist entries `Filament\Infolists\Components\`, layout components (`Grid`, `Section`, `Fieldset`, `Tabs`, `Wizard`) `Filament\Schemas\Components\`, schema utilities (`Get`, `Set`) `Filament\Schemas\Components\Utilities\`, and **every** action `Filament\Actions\`. Icons are the `Filament\Support\Icons\Heroicon` enum.

## Testing

Every change must be covered by a test. Three suites are registered in `phpunit.xml`, and `tests/Pest.php` binds all of them to `Tests\TestCase`:

- **Feature** (`tests/Feature/`) — application behaviour; gets `RefreshDatabase`. Grouped by product area:
    - `Account/` — signed-in user's own surfaces (profile, settings, the dashboard's in-progress list, notification bell, comment emails)
    - `Auth/` — Spotify OAuth login, callback and logout
    - `System/` — application-wide plumbing rather than a product area (session toasts)
    - `Discovery/` — public browse surfaces (explore feeds, leaderboards)
    - `Pages/` — content-driven pages (about, faq, legal documents, error pages)
    - `Rankings/` — the core ranking domain (setup, algorithm, comments, export, management)
    - `Tierlists/` — the tier list domain (setup, builder, board, limits, management)
    - `Reviews/` — the review domain (setup, creation, limits, body cleaning, management, show page, comments)
    - `Billing/` — Song Rank Pro: checkout, Stripe webhooks, licences, the billing page
    - `Catalog/` — crates: limits, settings, moving and ordering, filing records, the picker, the pages, the public catalog
- **Filament** (`tests/Filament/`) — the admin panel; gets `RefreshDatabase`. **Mirrors the `app/Filament/` directory structure**, so a test sits at the same path as the code it covers:
    - `app/Filament/Resources/Rankings/…` → `tests/Filament/Resources/Rankings/…`
    - `app/Filament/Widgets/…` → `tests/Filament/Widgets/…`
    - Name files after the surface under test (`RankingTableFiltersTest`, `TierlistInfolistTest`, `LoginsWidgetTest`), not after the resource as a whole — one resource has several surfaces (form, table, infolist, filters, relation managers)
- **Platform** (`tests/Platform/`) — codebase-wide checks that aren't feature behaviour, e.g. Pest arch tests. No `RefreshDatabase`.

Anything under `app/Filament/` is tested in the **Filament** suite, not `Feature`. Everything else goes in the `Feature/` directory matching its product area; add a new subdirectory only when an area has no existing home.

#### Testing Pro and the Admin Panel
- No feature flag needs setting up in a test: every domain is open to any signed-in user. `proUser()` builds a user holding an active licence, and `revokePro()` takes Pro away again
- The admin panel is gated on `is_dev`, so act as `kyle()` — the project's only admin persona — there
- Filament pages and widgets are Livewire components — test them with `Livewire::actingAs($user)->test(ListRankings::class)`, passing `['record' => $model->getKey()]` for view/edit pages

#### Test File Structure
Every Pest test file follows this order, top to bottom:
1. **Imports** — model/class `use` statements, then `use function Pest\Laravel\...` function imports
2. **`beforeEach()`** — shared arrangement (only when needed)
3. **`describe()` blocks** — every test lives inside a describe group
4. **Helper functions** — file-specific helpers at the bottom

Additional conventions:
- Use `Pest\Laravel` functions (`get()`, `actingAs()`, `assertGuest()`, ...) instead of `$this->get()` etc. — Intelephense cannot resolve `$this` inside Pest closures
- Avoid `$this->property` state in `beforeEach()` for the same reason; prefer helper functions
- Cross-file helpers live in `tests/Helpers/`, grouped by the domain they build for (`users.php`, `rankings.php`, `tierlists.php`, `reviews.php`, `catalog.php`, `spotify.php`, `stripe.php`) and required from `tests/Pest.php`. `alerts.php` holds `alertsFrom()`, which reads the sweetalert2 `flash`/`confirm` payloads a component sent on its last request, and `filament.php` holds `widgetStats()` / `widgetChartData()`, which read a dashboard widget's numbers. Helper function names are global, so they must be unique across the whole suite and specific (`tierlistBoard()`, not `board()`); anything used by a single test file still lives at the bottom of that file

#### The Outside World
- `Tests\TestCase::setUp()` seals every test: `Http::preventStrayRequests()`, a Stripe client that fails every call as if Stripe were down (`fakeStripeServices()` swaps in stand-ins), and every Discord log channel sent to a `NullHandler`. `phpunit.xml` pins dummy Spotify and Stripe credentials, `LOG_CHANNEL=null` and `NIGHTWATCH_ENABLED=false`, so a run never uses `.env` secrets or writes to `storage/logs`, and the suite passes offline
- The Spotify actions catch every exception, so a blocked stray request is swallowed rather than failing a test. A guard that should stop a Spotify call needs `Http::fake()` first and `Http::assertNothingSent()` last

#### Assertions
A test passes or fails on behaviour, never on wording. Prefer, in order: **state** (a component's computed collection via `->instance()`, `assertSet`, `assertViewHas`, the database), then **structure** (a route URL, a `wire:` hook or `wire:key`, `assertSeeLivewire`), then **behaviour** (redirects, dispatched events, `assertForbidden()`, alert payloads by `icon` or `action`).
- Never assert interface copy (headings, labels, placeholders, alert titles), a record's name in rendered HTML, or a bare number. When only a rendered string will do, derive it from the app (`$status->label()`, `$license->formattedTotal()`)
- Guard against vacuous assertions: test the component with `Livewire::test()` when the layout's nav or `<head>` would also contain the value, and pair every negative assertion with a positive control
- Filament: `assertTableColumnStateSet()` for columns, `->key()` on infolist sections with `assertSchemaComponentVisible()` / `Hidden()`, `TestAction` for actions, `widgetStats()` for widgets
- Derive limits from `config()` or pin them in `beforeEach`; build data with factories rather than seeded rows; order anything compared as a list; start rankings from `sortingStateInOrder()` rather than the shuffle
- Prove a new assertion by breaking the behaviour and watching it fail. After editing a Blade file to do that, run `php artisan view:clear`
